# AI Tooling Used to Build This Project

This project's codebase, synthetic policy corpus, mock data, tests,
evaluation harness, and documentation were generated by an agentic build
process using Claude (Claude Sonnet, running as a coding agent with shell,
file, and search tools) inside a sandboxed Linux environment, working from a
detailed spec. This document is an honest account of what worked well and
what needed correction during that build, written from the build process's
own experience, not a generic AI-disclosure template.

## What the agent produced

- All application code: FastAPI web app, agent orchestrator, MCP client and
  MCP server (8 tools), RAG pipeline (parsing, chunking, embedding,
  ingestion, retrieval), configuration.
- The entire synthetic policy corpus (12 documents, 3 formats) and mock
  structured data (employees, PTO balances, benefits, tickets) — original
  content written for this fictional company, not copied from a real
  employer's policies.
- The test suite, CI workflow, Render deployment config, evaluation set and
  harness, and all project documentation (this file, the design doc, the
  README).

## What worked well

- **Scaffolding a multi-component system from a single detailed spec.**
  Given the stack decisions up front (FastAPI, Chroma, sentence-transformers,
  Anthropic SDK, `mcp` package, stdio transport), the agent could generate a
  coherent set of modules with consistent interfaces (e.g. `LLMClient` and
  `MCPToolClient` as clean seams for dependency injection in tests) without
  needing much back-and-forth.
- **Writing substantive, structurally consistent synthetic content.** The
  12-document policy corpus needed to be original, realistic, internally
  consistent (cross-references between documents had to actually point to
  real doc_ids and match each other's numbers — e.g. the PTO Policy's
  "5 or more consecutive days -> check Leave Policy" cross-reference), and
  heading-structured for the chunking strategy. This is exactly the kind of
  long-form, consistency-constrained writing task where an LLM is efficient
  it produced all 12 documents, in 3 different formats, without needing
  manual editing for tone or structure.
- **Root-causing environment failures rather than working around them
  cosmetically.** The build sandbox had two nontrivial constraints: it could
  reach `pypi.org` but not `huggingface.co`, and its output directory was a
  FUSE mount that couldn't satisfy SQLite's file-locking requirements. In
  both cases the agent diagnosed the actual cause (via `curl` probes and
  reading tracebacks carefully) and adopted a solution that is a genuine
  improvement for the shipped project — loading the embedding model from a
  local, pip-installable package instead of at-runtime from the Hub, and
  documenting a filesystem caveat rather than baking a sandbox-specific path
  into the default config — rather than just hard-coding something that only
  worked in the sandbox.
- **Test-driven debugging of an async transport issue.** An anyio "cancel
  scope in a different task" error surfaced when using a per-test
  yield-fixture for the MCP client. The agent iterated through several fixes
  (adjusting fixture scope, forcing session-scoped event loops via
  pytest-asyncio ini options, and finally structuring the fixture as a
  passthrough over one session-scoped connection) until arriving at a
  version that passed reliably and quickly, rather than stopping at the
  first plausible-looking fix.

## What needed correction / would need a human's judgment call

- **The first MCP package version installed (2.0.0) had a substantially
  different high-level API** (`mcp.server.mcpserver.MCPServer` instead of
  the widely documented `mcp.server.fastmcp.FastMCP`) than most existing
  documentation and examples assume. The agent caught this by directly
  inspecting the installed package rather than assuming the API matched
  older tutorials, and deliberately pinned to the 1.x line instead for API
  stability and documentation coverage. This is the kind of "don't trust
  that the newest version behaves like older docs describe" check that
  still benefits from an engineer reviewing the actual dependency footprint,
  not just the code that was written against it.
- **Pinning `torch` without pulling multi-gigabyte CUDA dependencies**
  required an iterative process (checking wheel sizes across several
  version pins before finding one that resolved to a genuinely CPU-only
  build for the sandbox's architecture) rather than a one-shot correct
  answer. A human reviewer should double check that the pinned `torch`
  version continues to resolve to a CPU-only wheel as PyPI's packaging
  conventions evolve, since this is exactly the kind of thing that can
  silently regress on a dependency upgrade.
- **The deterministic (no-LLM) fallback intent router in the orchestrator is
  keyword-based** (checking for substrings like "pto", "remote", "benefit").
  This is intentional and clearly labeled (`llm_used: false`) — it exists
  specifically so the two required demo workflows and most of CI can run
  without an API key — but it is not a substitute for the real LLM tool-use
  loop's judgment, and a human should not mistake its coverage (a handful of
  hand-written intents) for general natural-language understanding. The eval
  harness surfaces this distinction explicitly in its output.
- **Nothing in this build was verified against the real Anthropic API**,
  since no key was available in the build sandbox by design. The LLM-mode
  code path (the actual agentic tool-use loop) was exercised only against a
  fully scripted stub client in tests. This is flagged clearly in the
  README, the design doc, and the evaluation results, and is the single
  biggest remaining verification gap — a human running this with a real key
  should specifically watch the first few real tool-use loop responses for
  anything the stub-based tests couldn't catch (e.g. how Claude actually
  phrases citations, or whether it ever tries a tool call the fallback
  router never had to handle).
